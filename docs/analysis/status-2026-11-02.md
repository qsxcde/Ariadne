## 1. 结论摘要

**一句话**：SciPal 已经完成从「能跑的 RAG demo」到「单机可用的论文问答应用 v0.1」的升级，后端分层、契约链和测试网是真实资产；但距离「可部署、可运营、可多人用」还差三块——前端测试与产品完成度、真实 RAG 链路的测试覆盖、部署与可观测性。

| 维度 | 评分 | 依据 |
|---|---|---|
| 架构分层 | 8/10 | `api / application / rag / adapters / storage / core / domain / worker` 边界清晰，且有 AST 静态校验（`tests/test_package_boundaries.py:72-98`） |
| 后端实现 | 7/10 | 主链路异常闭环、快照原子提交/回滚、SSE 协议校验都在（`application/indexing.py:185-247`、`api/streaming.py:87`）；仍是同步 IO + 单进程模型 |
| 测试 | 6/10 | 后端 128 例全绿、语句覆盖 60%；前端只有 1 个 spec / 5 例 |
| 契约与文档 | 6/10 | `schemas → contracts/openapi.json → openapi.d.ts` 闭环且 CI 有 diff 门禁；wiki 仍有多处停留在整改前 |
| 前端完成度 | 5/10 | 阅读器 + 引用定位是亮点；测试空白、两个巨石组件未拆、`status` 事件未呈现 |
| 部署与运维 | 3/10 | 无 Dockerfile/compose、无 metrics/trace；SQLite + 进程内队列，天然单实例 |
| **综合** | **6.5/10** | 单机自用约 8/10；多人、多实例上线约 4/10 |

**三条主要判断：**

1. **整改是真落地，不是文档工程。** P0–P7 声称的成果大部分能在代码里复核：契约生成链、SSE 心跳、job 恢复、类型检查、前端域目录与 stores 出口都存在，且本次实跑全部门禁通过。
2. **风险已经转移。** 从「代码能不能跑」变成「测试结构失配 + 文档漂移 + 默认开发体验有洞」——这类问题不会让演示失败，但会让下一次改动和交接变贵。
3. **产品边界清晰但窄。** 只支持文本型 PDF、单会话单 active snapshot、PC Web；这是合理的 v0.1 取舍，但决定了它目前还不是「跨论文的智能助手」。

## 4. 已经具备的能力（可信资产）

- **快照式索引与原子提交**：候选快照构建成功才 promote，失败回滚，避免 SQLite 与 FAISS 状态分裂（`application/indexing.py:185-247`）。
- **传输层与领域事件解耦**：领域事件到 SSE 的映射有显式校验，未知事件直接 `TypeError`，不会静默丢事件（`api/streaming.py:74-87`）。
- **流式生命周期**：独立 `ThreadPoolExecutor` 推进同步生成器，避免占用全站默认线程池（`application/chat.py:31`、`:96`）；15s 心跳解决空闲断连。
- **启动恢复**：启动时恢复孤儿文档与中断 job（`main.py:68-76`）；job 消费用 CAS 防重复执行。
- **契约单一真值**：Pydantic schema → OpenAPI → TypeScript 类型，CI 对生成结果做 diff 门禁；README 端点表也由脚本生成。
- **分层守卫**：`tests/test_package_boundaries.py` 用 AST 检查依赖方向，`api/` 不碰存储、`storage/` 不依赖 RAG。
- **引用闭环**：后端产出 `SourceRef`，前端 `PaperReader` / `PdfViewer` / `SourceDrawer` 支持正文定位与 PDF 原页高亮。

## 5. 问题清单

### P0（阻塞发布）

**无。** 当前没有发现会导致数据损坏、鉴权绕过或主链路必现失败的问题；生产鉴权缺失时启动会直接失败（`main.py:29-45`）。

### P1（明显影响交付质量）

1. **前端测试与 7k 行代码严重失配。**
   全仓库只有 `frontend/src/composables/__tests__/useChatStream.spec.ts` 一个 spec，5 个用例。上传轮询、会话状态机、阅读器引用定位、错误重试这些高风险路径没有任何回归网；后端每次重构有 128 例兜底，前端等于裸奔。

2. **默认开发模式下「文献库」页不可用。**
   `frontend/vite.config.ts:11-14` 只代理了 `/auth`、`/sessions`、`/health`，但文献库调用的是 `GET /documents`（`frontend/src/api/library.ts:6`）。仓库里只有 `.env.example`、没有 `frontend/.env`，默认走同源相对路径，于是 `/documents` 会落到 Vite 的 SPA fallback，返回 HTML，前端 JSON 解析失败。生产反向代理若覆盖全路径不受影响，但「clone 下来按 README 启动」的默认体验是坏的。

3. **RAG 与适配层是覆盖率洼地。**
   总覆盖 60%，但主链路 `application/chat.py` 89%、`documents.py` 84%、`indexing.py` 86% 都不错；真正与外部世界打交道的模块反而低：`rag/retrieval/context_builder.py` 21%、`rag/retrieval/bm25.py` 25%、`adapters/llm/model_client.py` 30%、`adapters/embedding/local_embedder.py` 25%、`adapters/vector/store_cache.py` 37%。**测试网保护了「状态与索引工程」，没有保护「检索质量与模型接入」。**

4. **CI 不验证真实 RAG 依赖。**
   这是 P1-3 的制度化版本：CI 为了速度不装 torch/faiss/openai，真实向量检索、远程 embedding、LLM 流式解析在 CI 中全部跳过。建议至少加一个「精简依赖 + fake 模型」的契约测试层，让这些路径在 CI 里有行为断言。

### P2（体验、可维护性与运维）

1. **文档漂移**：详见第 6 节。最典型的是 wiki 仍写 schema v5，代码已是 v7；07 章仍写「路由未注册」。
2. **`status` / `warning` 事件被前端丢弃**：`useChatStream.ts:86-92` 收到后直接 `break`，用户看不到「等待索引 / 检索中 / 生成中」，也看不到降级告警；后端已经发了这些事件。
3. **结构遗留**：`PaperReader.vue` 587 行、`LibraryPanel.vue` 471 行仍未拆（remediation-plan 的 P5 最后一步）；8 个 `rag/` 模块仍在模块作用域直接读全局 `settings`（如 `rag/ingestion/pipeline.py:80`、`rag/ingestion/mineru_backend.py:23`）。
4. **部署与运维缺位**：无 Dockerfile / compose / 部署脚本；无 metrics、trace、请求 ID；进程内 job runner + SQLite 决定了只能单实例。当前定位是本地工具，这不算缺陷，但一旦要多人使用就是硬约束。
5. **仓库卫生**：`origin/docs`、`origin/feat`、`origin/fix` 三个远端分支都停在初始原型提交 `8752372`，落后 `main` 99 个提交；无 tag，版本仍是 `0.1.0`。

## 8. 验证方法与局限

- 已执行：上述 9 项门禁 + `sqlite3` 检查开发库版本 + `git` 分支/提交统计。
- 未执行：真实 DeepSeek / MinerU / embedding 调用的端到端回归；浏览器手工走查；并发压测；多用户隔离测试。

- 评分是工程判断，不是精确指标；「单机自用 8/10、多人上线 4/10」是按两种使用场景拆分的结果。
