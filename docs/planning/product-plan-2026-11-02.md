# 智能论文助手功能规划（2026-11-02）

> 目标：在 SciPal 现有「单篇 PDF + 会话式 RAG」基础上，规划一个真正帮助研究人员**读论文、管理阅读进度、跟进领域进展**的产品。
> 前置阅读：[现状分析](../analysis/status-2026-11-02.md)、[能力缺口分析](../analysis/gap-analysis-2026-10-25.md)、[系统架构](../wiki/02-architecture.md)
> 本文回答三个问题：做什么、先做什么、为什么；不含排期承诺。

## 0. 一句话结论

把产品从「论文问答器」升级为「研究工作台」，核心不是再加几个 AI 按钮，而是补上三层资产：**论文实体（paper）、阅读状态（reading state）、跨论文知识（collection）**。功能顺序必须是：

**先资产、后智能；先单篇、后跨篇；先进度、后跟进。**

## 1. 目标用户与场景

**已确认（2026-11-02）：**

- 目标用户：**个人用户，研究生**；每周读 3–15 篇论文；中文母语，英文论文为主。
- 使用形态：PC Web，单机/私有部署优先；**不做团队协作与多租户**。
- 产品重心：**阅读进度优先**；领域跟进（C）是可选增长项，不作为核心承诺。
- 实施顺序：**先做数据模型重构（M0），验收后再上 AI（M1+）**。

**核心痛点：**
  1. 读完就忘，笔记散落，无法回溯「当时为什么觉得这篇重要」。
  2. 不知道下一篇该读什么，阅读队列越积越多。
  3. 领域新论文太快，靠刷 arXiv / 社交平台，漏读、重复读。
  4. 写 related work 时，需要手工对比多篇论文的方法、数据集与结论。

**产品承诺：**

- **读得完**：每篇论文都有明确的「读到哪里、读懂了什么、还欠什么」。
- **读得懂**：所有解释、摘要、对比都能回到原文，不产生无依据的结论。
- **跟得上**：只推「与当前研究相关」的新论文，并说明为什么相关。

## 2. 先把「进度」定义清楚

「跟进论文进度」至少有三层，不能混在一个功能里：

| 进度类型 | 用户问题 | 产品载体 | 本期优先级 |
|---|---|---|---|
| A. 阅读进度 | 这篇我读到哪了？读懂了吗？ | 论文状态、阅读位置、笔记、开放问题 | 最高（M0/M1） |
| B. 项目进度 | 这个课题/综述还差哪些论文？ | 集合/项目、阅读队列、周报 | 高（M1/M2） |
| C. 领域进度 | 最近这个方向有什么新论文？ | 订阅、Feed、提醒、Digest | 中（M3） |
| D. 写作进度 | 我的论文写到哪了？ | 里程碑、章节草稿 | 不做（另一个产品） |

本期聚焦 **A + B**。C 在 M0–M2 稳定后再评估，且只做「低打扰的订阅/Feed」，不追求大而全的文献发现；D 属于项目管理，不混入阅读助手，避免产品失焦。

## 4. 核心用户旅程

### 4.1 阅读闭环（单篇）

```
导入（L2/L3） → 自动解析（现有 ingestion） → 5 分钟速读卡（R2）
   → 决定：归档 / 进队列 / 立即精读（P1/P4）
   → 章节阅读 + 划词解释/翻译（R1/R3/R4）
   → 高亮/批注/笔记（R7）
   → 追问（R9/R12） → 标记已读（P1/P2）
   → 导出笔记（S1）
```

关键设计：**每一步都写入阅读状态**，而不是让用户手动维护一个 Excel。

### 4.2 进度闭环（项目/领域）

```
设定本周目标（P5） → 队列排序（P4）
   → 阅读状态自动更新（P2/P3）
   → 周报：读完什么、留下什么、还欠什么（P5/P7）
   → 订阅相关主题（F1） → Feed（F2/F4）
   → 保存到队列（F5） → 回到阅读闭环
```

关键设计：**Feed 不是第二个收件箱**。没有队列和阅读状态，推荐只会增加焦虑；所以 F 层必须排在 P 层之后。

## 5. 分阶段路线图

### M0 · 资产基础（必须先做）

**目标**：把「论文」从会话附件升级为独立实体，让进度可持久化。

> 详细设计（表结构、迁移步骤、API、测试与验收）见 [M0 论文资产层设计](m0-paper-model-2026-11-02.md)。

功能点：L1、L2、L5、L6、L7、P1、P2、R7、T1；R1 补「上次位置」。

验收标准：

- 已有会话可迁移：每篇 `documents` 生成一条 `papers` 记录，旧链接不丢。
- 文献库可按状态/集合/标签筛选；同一 PDF 不重复入库。
- 论文状态与阅读位置刷新后不丢；笔记能锚定到原文 chunk。
- 现有 128 个后端用例全绿，新增迁移与状态持久化用例。

### M1 · 阅读助手 MVP

**目标**：让用户第一次感到「它真的帮我读懂了」，而不只是「能问答」。

功能点：L3、L8、R2、R3、R4、R8、R12、P4、T2、T3。

验收标准：

- 导入一篇论文后，能生成带章节/页码引用的速读卡；无依据的结论不出现。
- 划词「解释/翻译」在阅读器内完成，结果可一键存为笔记。
- 阅读队列可排序；标记「在读/已读」后，Dashboard 数字同步变化。
- 所有 AI 产出的段落都能点击回到原文位置。

### M2 · 进度与跨论文

**目标**：从「读一篇」升级为「管理一个课题」，并让进度形成复盘。

功能点：L4、R5、R6、R9（集合）、R10、P3、P5、P6、P7、P8、S1、S4、T4、T5、T6。

验收标准：

- 集合内问答能跨 2 篇以上论文作答，引用必须带 paper 标识。
- 能生成「方法/数据集/指标/结论」对比表，并导出 Markdown/CSV。
- 周报能自动汇总：本周读完、笔记、开放问题、下周队列。
- 集合维度能看到已读/在读/待读，而不是只看到会话列表。

### M3 · 跟进领域（可选，M2 验证后再决定）

**目标**：让用户不再靠刷信息流跟论文。个人研究生场景下，这不是核心承诺；只有在 M1/M2 的阅读闭环跑通、用户明确表达「跟新论文」需求后才启动。

功能点：F1–F5。

验收标准：

- 能订阅关键词/作者/venue，Feed 只出现未读、未忽略的论文。
- 每条推荐都有「为什么推给我」的解释，且可一键存入阅读队列。
- 同一论文多来源去重；已读论文不再重复推荐。
- 用户能从 Feed 直接进入阅读闭环，不需要重新上传。

### M4 · 沉淀与提醒

**目标**：把阅读沉淀为可复用知识，并降低跟进成本。

功能点：F6、F7、F9、R11、S2、S3、L9。

验收标准：

- 日报/周报可配置；新论文、新版本、新引用可提醒。
- 笔记与综述矩阵可导出到 Markdown/CSV；Zotero 双向同步可用。
- 引用网络能回答「这篇被谁引用 / 它引用了谁」。

### M5 · 协作与规模化（不做）

已确认目标用户是个人研究生，**团队协作、共享笔记、多租户不在本期范围**。移动端采集也暂缓；先把 PC Web 的单人阅读闭环做扎实。

## 6. 优先级矩阵

| | 低成本 | 高成本 |
|---|---|---|
| **高价值** | 阅读状态/进度、5 分钟速读卡、章节摘要、划词解释/翻译、高亮笔记、文献库筛选、arXiv URL 导入、引用跳转 | 集合级 RAG、多论文对比、Feed 推荐、引用网络、Zotero 同步 |
| **低价值** | 标签颜色、阅读 streak、分享卡片、主题皮肤 | 自建文献管理器、全量爬虫、原生移动 App、早期团队协作 |

**判断规则**：任何功能如果不能回答「它让下一篇论文更容易读完/读懂/找到」，就暂缓。

## 7. 与现有代码的差距

| 能力 | 现状 | 需要改什么 |
|---|---|---|
| 论文身份 | `documents.session_id` 非空，论文隶属于会话（`storage/sqlite/schema.py:218-235`） | 新增 `papers`；`documents` 增加 `paper_id`，会话只作为对话容器 |
| 阅读状态 | 无表、无字段 | 个人单用户场景下直接放在 `papers`：reading_status / progress / last_location / last_read_at / time_spent_seconds；暂不拆 `reading_states` 表 |
| 批注笔记 | 无表 | 新增单表 `annotations`（type=highlight/note/question），锚定 `chunk_id` / page / bbox；笔记是 type=note 的 annotation，不单开表 |
| 集合与项目 | 只有 session 列表 | 新增 `collections` / `collection_papers` |
| 跨论文检索 | 快照按 `session_id` 组织（`schema.py:297-307`） | 新增 collection 级快照与 `paper_id` 过滤；单篇索引保留 |
| 引用标识 | `SourceRef.paper_id` 实际承载的是 `document_id`（`storage/sqlite/chunks.py` 的 `_row_to_chunk`），`domain/models.py:39-43` 只有 section/chunk | M0 不改内部命名：API 同时返回真实 `paper_id` 与 `document_id`；M2 做集合检索时再统一命名 |
| 摄取与索引归属 | `documents.session_id`、`index_snapshots.session_id` 非空（`schema.py:218-235`、`297-307`） | M0 保留「每篇 paper 自动创建一个 reading session」以复用现有摄取/索引；M2 再上移 collection scope |
| 文献库 | `GET /documents` 是跨会话视图（`frontend/src/api/library.ts:6`） | 新增 `/papers` 资源与 `/collections` |
| 解析产物 | `DocumentIR` 已含 outline / quality report（`rag/ingestion/document_ir.py:71-80`） | 直接复用到速读卡、章节导航、质量提示 |
| 阅读器 | `PaperReader` / `PdfViewer` 已支持引用定位 | 复用并增加批注层、笔记侧栏、进度上报 |
| 评测 | `scipal_eval` 覆盖检索/RAGAS | 增加摘要忠实度、对比准确性、推荐相关性 |
| 任务队列 | 单进程、会话级串行（`worker/runner.py`） | 增加 feed 抓取/批量解析 job；明确单实例约束 |

**迁移策略（重要）**：不要一次性重写。M0 采用「paper 是资产，session 是阅读/索引容器」的最小改造：每篇 paper 自动创建一个 reading session，`documents` / `chunks` / `jobs` 增加 `paper_id` 并回填；**不拆 `documents.session_id` 的非空约束**，避免重写摄取与索引链路。旧会话 API 保留，新增 `/papers` API 双轨。等 M2 做集合检索时，再把索引 scope 从 session 上移到 collection。

## 8. 指标

**北极星指标**：每周「读完并留下笔记」的论文数。它同时反映阅读、理解和沉淀，不容易被刷。

| 环节 | 指标 |
|---|---|
| 激活 | 导入 → 生成速读卡 → 首条高亮/笔记 → 首次提问的转化率 |
| 阅读 | 论文完成率、从导入到首条笔记的时间、每篇笔记数 |
| 进度 | 队列平均停留天数、周目标达成率、积压量 |
| 跟进 | Feed 保存率、忽略率、Digest 打开率、新论文→阅读转化 |
| 信任 | 引用点击率、摘要点赞/点踩、幻觉反馈率 |
| 留存 | 周活跃、4 周留存 |
| 成本 | 每篇速读卡 token 成本、每次问答成本、缓存命中率 |

## 9. 风险与非目标

| 风险 | 缓解 |
|---|---|
| 范围失控，做成半成品 Zotero | 不自建文献管理器；元数据用 OpenAlex/Crossref，文献管理用 Zotero 集成 |
| 数据模型迁移破坏现有会话 | 增量 schema + 双写 + 回填 + 迁移测试；旧 API 保留 |
| 外部源限流、元数据缺失、PDF 不可得 | 只用开放 API 与用户上传；缓存元数据；允许手工修正 |
| 摘要/对比幻觉 | 所有结论带 provenance；无依据拒答；评测门禁 |
| LLM 成本失控 | 按需生成、按论文版本缓存、批量任务、可配置模型 |
| 进度追踪变成监控 | 默认只记录必要信息；允许手动修正与关闭；本地优先 |
| Feed 变成第二个收件箱 | 推荐必须可执行（存队列/忽略），且与阅读状态联动 |

**明确不做：**

- 不做完整参考文献管理器（Zotero 替代品）。
- 不爬取付费墙后的全文。
- 不在 M0–M2 做团队协作、移动端原生 App。
- 不对全库论文预生成摘要；按需生成并缓存。
- 不输出没有原文依据的「总结」。

## 10. 建议的第一个迭代

不要先做 Feed，也不要先做多论文对比。先做一条**可验证的最小闭环**：

1. schema v8：`papers` / `collections` / `annotations` / `paper_tags`，给 `documents` / `chunks` / `jobs` 增加 `paper_id`，完成旧数据回填。
2. 文献库：按状态（inbox / queued / reading / read）列出论文，支持导入与打开。
3. 阅读器：记录最后位置与进度；高亮 → 笔记 → 笔记列表。
4. 一个 AI 功能：**带 provenance 的 5 分钟速读卡**（复用现有 RAG 与解析产物，不新增模型能力）。
5. 验收：导入 → 打开 → 标记在读 → 高亮记笔记 → 关闭再打开能续读 → 速读卡引用可回跳。

详细执行顺序见 [M0 论文资产层设计](m0-paper-model-2026-11-02.md)。这条闭环跑通后，再决定 M2 先做「进度 Dashboard」还是「多论文对比」——那时你已经有真实用户数据，而不是靠猜。

## 11. 已确认的决策与影响

| 决策 | 结论 | 对规划的影响 |
|---|---|---|
| 目标用户 | 个人研究生 | 去掉团队协作、共享、多租户；单机/本地优先；权限模型保持现状即可 |
| 进度重心 | 阅读进度（A） | M0/M1 先做状态、位置、笔记、队列；领域跟进（C）降为可选 |
| 实施顺序 | 先数据模型重构，再上 AI | M0 必须先验收；M1 不提前动 schema；M0 期间冻结新的 AI 功能 |

**仍需用真实用户验证的，不是方向，而是细节**：哪些阅读动作最耗时（速读、翻译、公式、图表）、笔记导出到哪里、阅读队列如何排序。这些应在 M1 上线后用 5–8 位研究生的实际使用数据决定，而不是继续扩功能清单。
